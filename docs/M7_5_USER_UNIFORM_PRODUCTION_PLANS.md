# M7.5 — пользовательские uniform production plans

Дата: 2026-07-27.

## Цель

Подключить реальные пользовательские поля главной страницы к производственному ядру. Пользователь вводит собственные:

- исходный формат листа;
- зачистку и непечатные поля;
- общий формат изделия;
- выпуск и зазор;
- строки `файл | тираж | страниц | примечание`;
- общую цветность лица и оборота;
- плотность и рабочие цены.

После этого программа строит не демонстрационные карточки, а materialized front/back layouts, независимо проверенные production reports и нормализованные `SolutionMetrics`.

## Текущая область полного перебора

На этом этапе полностью рассматривается явно ограниченное пространство:

- один общий формат изделия для всех строк;
- каждая fitting uniform-grid ориентация: `0°` и `90°`;
- отдельные лицевые и оборотные формы;
- две plan-family для каждой ориентации:
  1. paper-focused план существующего minimizer;
  2. отдельная полностью заполненная форма на каждую печатную пару;
- одна общая цветность для всех строк заказа;
- только полные пары лицо/оборот.

Если обе ориентации помещаются, каталог содержит четыре плана. Если помещается одна — два плана. Ни один допустимый план внутри этой области не удаляется.

## Paper-focused результат

Существующий minimizer вычисляет универсальную нижнюю границу бумаги и строит допустимый план.

Название `Proven paper minimum` используется только когда построенный результат достиг нижней границы. Если граница не достигнута, интерфейс честно показывает `Paper-focused feasible plan` и не заявляет доказанный минимум.

## Проверка каждого плана

Каждый план проходит одну и ту же цепочку:

1. кандидат materialize-ится в лицевую форму;
2. оборот строится зеркалированием;
3. `validateImposition` проверяет геометрию и пары страниц;
4. `buildProductionReport` независимо пересчитывает выпуск;
5. недопечатка должна быть равна нулю;
6. `SolutionMetrics` получает реальные листы, формы, пластины, прогоны, перетираж и фрагментацию;
7. при готовом прайсе рассчитывается себестоимость в BYN;
8. план передаётся в lossless-каталог.

## Цветность

`createProductionReportSolutionMetrics` теперь принимает явный `printSpecification`.

Для `4+1` на один монтаж учитываются:

- две layout-формы — лицо и оборот;
- пять цветовых пластин — четыре на лице и одна на обороте;
- два прогона каждого физического листа.

Рабочие цены не подставляются автоматически. Без прайса все неденежные варианты остаются доступными, а денежная цель временно исключается из ранжирования.

## Каталог на главной странице

Панель `Варианты пользовательского заказа` по умолчанию показывает все планы.

Фильтры:

- `Все`;
- `Pareto`;
- `Рекомендуемые`;
- `Доминируемые`.

Фильтр меняет только представление. Он не удаляет решения из каталога и не запускает повторную генерацию.

Карточка показывает:

- ориентацию и сетку;
- физические листы;
- layout-формы;
- цветовые пластины;
- листопрогоны;
- перетираж печатных пар;
- себестоимость;
- ранг;
- метки recommendation, Pareto, domination и одинаковых метрик.

## Mobile

Для ширины около `390 px`:

- фильтры размещаются в две колонки;
- карточки остаются вертикальными;
- метрики размещаются по две в строке;
- горизонтальный скролл каталога не требуется;
- focused mobile Chromium scenario проверяет тот же расчёт, что и desktop.

Это уже компактный рабочий каталог, но не финальная компактность всей длинной страницы.

## Защитные границы

### Нечётное число страниц

Парсер по-прежнему умеет показать последнюю страницу с пустым оборотом. Однако пользовательский production planner пока требует полные front/back пары. Такой заказ отклоняется до расчёта, чтобы общая цветность оборота не создала неверные пластины и стоимость для пустой стороны.

Поддержка потребует индивидуальной цветности и явной односторонней формы.

### Ограничение интерактивного расчёта

Главная страница ограничивает пользовательский расчёт `500` печатными парами. Это защита интерфейса до появления отдельного тяжёлого search worker с отменой и прогрессом.

### Что пока не входит

- mixed-format packing;
- смешанные повороты внутри листа;
- произвольные последовательности всех возможных форм;
- общий автоматический work-and-turn для пользовательского заказа;
- индивидуальные формат, выпуск и цветность каждой строки;
- цена продажи, выручка и прибыльность;
- сохранение проекта;
- экспорт выбранного пользовательского плана в PDF.

Поэтому текущая программа может сравнивать себестоимость, но ещё не может доказать, что заказ убыточный: для этого нужна цена продажи или выручка.

## Доказательство полноты

`completeWithinDeclaredFamilies: true` означает только полный перебор fitting `0°/90° × две plan-family`.

`globalCompletenessClaimed` остаётся `false`. Интерфейс всегда показывает эту границу рядом с количеством вариантов.
