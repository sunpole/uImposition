# uImposition — operator-first product rebuild

Дата решения: **31 июля 2026**.  
Основная задача: **Issue #64**.  
Статус: **обязательный продуктовый контракт для новой пользовательской оболочки**.

## 1. Почему направление изменено

Расчётное ядро uImposition содержит полезные и проверенные модули: геометрию, page pairs, front/back validation, production reports, стоимость, lossless-каталог, выбор оператора и PDF. Но пользовательская оболочка развивалась последовательными панелями поверх исторической demo-страницы.

Позднейшая попытка распределить эти панели по application shell не устранила фундаментальную проблему:

- интерфейс повторяет внутреннюю архитектуру модулей, а не работу оператора;
- один заказ разбит между множеством несвязанных экранов и технических блоков;
- старые и новые CSS-слои конфликтуют;
- layout нестабилен на разных ширинах;
- важные действия теряются среди diagnostics, milestone и evidence;
- простая работа требует понимания внутренних терминов;
- существующий UI нельзя безопасно довести до целевого продукта локальными правками.

Поэтому текущий UI признаётся **временным техническим прототипом**. Новая оболочка строится как чистый слой поверх сохранённого доменного ядра.

## 2. Главная цель продукта

Оператор должен без инструкции быстро пройти путь:

```text
выбрать лист
→ добавить виды продукции
→ сразу увидеть обновлённый расчёт
→ сравнить варианты монтажа
→ выбрать вариант
→ открыть схему
→ экспортировать результат
```

Программа должна ощущаться как рабочий производственный инструмент, а не как документация к алгоритму.

## 3. Основной рабочий сценарий

### 3.1 Быстрый выбор листа

В начале работы оператор видит компактные пресеты листов и машинных условий:

- встроенные рабочие форматы;
- пользовательские локальные пресеты;
- избранные;
- недавно использованные;
- действие `Новый пресет`.

Одно нажатие применяет:

- размер исходного листа;
- стадию размера до/после зачистки;
- зачистку по сторонам;
- фактический рабочий размер;
- непечатные поля машины;
- при необходимости связанные предпочтения бумаги и машины.

Пользовательский пресет сохраняется локально в браузере и имеет версионированную схему данных.

### 3.2 Быстрый ввод продукции

После выбора листа оператор добавляет строки продукции. Каждая строка представляет один реальный вид работы и содержит основные поля:

- название/идентификатор;
- готовая ширина и высота;
- тираж;
- количество страниц;
- количество одинаковых видов или файлов;
- цветность лица и оборота;
- односторонняя/двусторонняя работа;
- выпуск;
- рез/gap;
- допустимая технология оборота.

Редкие параметры скрыты под `Дополнительно`, но не вынесены в отдельный длинный документ.

Строку можно:

- добавить;
- дублировать;
- удалить;
- временно отключить;
- переименовать;
- переставить;
- сохранить как шаблон позднее.

### 3.3 Живой перерасчёт

Обычная работа не требует отдельной кнопки `Рассчитать` после каждого изменения.

После каждого корректного изменения единый pipeline обновляет:

- printable geometry;
- fitting и candidate layouts;
- production plans;
- physical sheets;
- layout forms;
- color plates;
- press passes;
- overrun;
- production cost;
- comparison results;
- preview выбранного варианта.

Для текстового ввода допускается короткий debounce, но пользователь воспринимает расчёт как синхронный и непрерывный.

Если данные неполны или ошибочны, интерфейс показывает локальную ошибку рядом с полем и сохраняет последний подтверждённый результат отдельно от чернового ввода.

## 4. Результаты, понятные оператору

Основной результат отвечает на производственные вопросы, а не показывает внутренние статусы модулей.

Каждый вариант содержит минимум:

- физические листы;
- массу/расход бумаги;
- layout-формы;
- цветовые пластины;
- листопрогоны;
- перетираж;
- количество монтажей;
- стоимость бумаги;
- стоимость форм/пластин;
- подготовку;
- полную себестоимость;
- ограничения и технологические предупреждения;
- краткое объяснение компромисса.

Основные представления:

1. **Минимум бумаги** — наименьший подтверждённый расход листов внутри текущей области поиска.
2. **Минимум форм** — сокращение форм/пластин с честным показом дополнительной бумаги и прогонов.
3. **Минимум стоимости** — минимум рассчитанной производственной себестоимости при полном прайсе.
4. **Производственно удобный** — отдельная операторская рекомендация только при наличии формализованных критериев; не выдумывается автоматически.
5. **Остальные допустимые** — полный lossless-каталог внутри заявленного bounded scope.

Recommendation остаётся меткой. Явный выбор оператора имеет приоритет и не заменяется при live reranking.

## 5. Целевая структура desktop

Desktop использует один основной workspace, а не последовательность длинных документов.

```text
┌──────────────────────────────────────────────────────────────────┐
│ проект · статус · язык · открыть/сохранить · настройки           │
├──────────────────────────────────────────────────────────────────┤
│ ПРЕСЕТЫ ЛИСТА / МАШИНЫ                                          │
│ [650×313] [616×446] [616×466] [636×448] [+ Новый пресет]         │
├───────────────────────────────────────┬──────────────────────────┤
│ ВИДЫ ПРОДУКЦИИ                        │ ЖИВОЙ ИТОГ               │
│ строки заказа                         │ листы/forms/plates/cost  │
│ [+ Добавить вид]                      │ readiness/errors         │
├───────────────────────────────────────┴──────────────────────────┤
│ ВАРИАНТЫ МОНТАЖА                                                 │
│ минимум бумаги · минимум форм · минимум стоимости · остальные   │
├───────────────────────────────────────┬──────────────────────────┤
│ сравнение вариантов                   │ схема выбранного         │
│                                       │ варианта и export        │
└───────────────────────────────────────┴──────────────────────────┘
```

Это логическая модель, а не обязательный пиксельный макет. Перед реализацией нового UI должны быть выбраны и зафиксированы визуальные решения.

## 6. Целевая структура mobile

Mobile не является сжатым desktop.

Основные экраны:

1. **Заказ** — пресет листа и строки продукции.
2. **Варианты** — компактное сравнение ключевых метрик.
3. **Схема** — выбранный вариант, preview и экспорт.

На экране одновременно находится одна главная задача. Введённые данные, выбранный вариант и последний корректный расчёт сохраняются между экранами.

## 7. Единое состояние приложения

Новая оболочка не должна управлять расчётами через разрозненные DOM-поля и независимые runtime-панели.

Минимальная структура:

```text
project
├── schemaVersion
├── sheetPresetId
├── sheet
├── press
├── products[]
├── pricing
├── objectivePreferences
├── draftValidation
├── calculationStatus
├── generatedPlanSet
├── selectedPlanId
├── lastValidSnapshot
└── ui
```

Правила:

- state является единственным источником пользовательского ввода;
- доменные функции получают plain data и не читают DOM;
- render-слой отображает state и dispatch-ит действия;
- тяжёлые вычисления позднее могут быть перенесены в Web Worker без изменения UI-контракта;
- persistence использует schemaVersion и явные migrations;
- raw layouts/reports не дублируются в browser events без необходимости.

## 8. Пересчёт и согласованность модулей

Целевой поток:

```text
user action
→ state reducer/action
→ normalized draft
→ validation
→ calculation request
→ domain pipeline
→ immutable calculation snapshot
→ comparison annotations
→ UI render
→ optional persistence
```

Требования:

- одно изменение создаёт один согласованный snapshot;
- устаревший асинхронный результат не может перезаписать более новый;
- filters/sort не перестраивают production plans;
- objective reranking использует готовые планы;
- selection сохраняется, пока plan ID существует;
- ошибки расчёта не уничтожают последний корректный результат;
- отсутствующая стоимость остаётся `unknown/null`, а не `0`.

## 9. Что сохраняется из текущего проекта

Сохраняются и повторно используются после проверки API:

- geometry и printable area;
- page-pair preparation;
- front/back derivation и validation;
- uniform candidate generation;
- current bounded minimizer;
- production metrics;
- production report;
- production cost;
- lossless feasible catalog;
- recommendation/selection semantics;
- PDF document models и renderers;
- unit/regression fixtures;
- GitHub Actions evidence pipeline.

Сохранение модуля не означает обязательное сохранение его текущего DOM-renderer или CSS.

## 10. Что не переносится в новый основной UI

Не являются основой новой оболочки:

- существующая длинная HTML-структура;
- app-shell, построенный перестановкой исторических панелей;
- цепочка CSS overrides;
- milestone/status/roadmap панели;
- control/evidence сценарии как рабочие пользовательские экраны;
- несколько конкурирующих summary;
- технические названия M3–M7 в основном workflow;
- отдельные большие панели каждой внутренней модели.

Исторические UI и evidence можно сохранить для regression и сравнения, но они не должны диктовать новую информационную архитектуру.

## 11. Сложные многовидовые раскладки

Полноценная цель продукта включает заказы, где одновременно присутствуют:

- разные форматы изделий;
- разные тиражи;
- разные количества видов;
- разные ориентации на одном листе;
- частично заполненные формы;
- повторения одного вида;
- несколько последовательных монтажей;
- разные компромиссы бумага/forms/plates/passes/cost.

Текущий uniform solver этого не реализует. Поэтому новый UI обязан честно различать:

- **доступный сейчас uniform calculation**;
- **будущий mixed-format/multi-product search**.

Сложный solver разрабатывается отдельными bounded plan-family с:

- deterministic signatures;
- explicit candidate limits;
- progress/cancel;
- truncation status;
- completeness claims только внутри заявленной области;
- independent validation каждого materialized плана;
- сохранением всех допустимых материально различных решений.

## 12. Порядок реализации

### R0 — остановка старого направления

- PR #62 не объединяется;
- дальнейшие UX-2/UX-4/UX-5 поверх старого DOM прекращаются;
- текущий `main` сохраняется как технический checkpoint;
- опубликованный `0.7.0-alpha.5` и immutable tag не изменяются.

### R1 — продуктовый контракт

- этот документ;
- синхронизация точек входа и status-документов;
- Issue #64 как основная задача;
- старый UI redesign contract получает исторический/superseded статус.

### R2 — pure state and presets foundation

Отдельный PR без новой визуальной оболочки:

- versioned project state;
- sheet/press preset model;
- built-in presets;
- local preset repository;
- migrations;
- deterministic serialization;
- unit tests.

### R3 — clean workspace foundation

Отдельный UI PR после выбранного визуального направления:

- чистая новая HTML/CSS структура;
- preset switcher;
- product rows;
- live validation/status;
- подключение текущего uniform pipeline;
- отсутствие старых рабочих панелей в новом flow.

### R4 — comparison and selected layout

- operator-focused result cards/table;
- paper/forms/cost views;
- exact deltas;
- selection;
- layout preview;
- existing selected-plan PDFs;
- desktop/mobile Chromium evidence.

### R5 — complex multi-product solver

Последовательность отдельных bounded PR, а не один гигантский patch.

## 13. Неприкосновенные производственные правила

- недопечатка всегда запрещена;
- оборот строится из проверенного лица;
- геометрия остаётся внутри печатной области;
- зачистка листа и поля машины являются разными этапами;
- layout forms и color plates не смешиваются;
- отсутствующая стоимость не превращается в ноль;
- operator selection не заменяется recommendation;
- filters меняют view, а не catalog data;
- bounded search не называется глобально полным;
- machine compatibility подтверждает оператор;
- новая расчётная логика создаётся как pure module с unit tests.

## 14. Stop condition первого цикла

Первый новый UI-цикл завершён только когда владелец на реальном рабочем заказе подтверждает, что может без объяснений:

1. выбрать или создать пресет листа;
2. добавить несколько видов продукции;
3. изменить тираж/формат и сразу увидеть новый результат;
4. понять различия по бумаге, формам и стоимости;
5. выбрать монтаж;
6. открыть схему;
7. скачать PDF.

До этого нельзя объявлять новый интерфейс завершённым или выпускать alpha.6 как удобный рабочий инструмент.

---

## English summary

The current calculation core remains valuable, but the existing panel-based interface is now treated as a technical prototype. The new product layer must follow the operator workflow: choose or create a sheet/press preset, enter real product rows, receive coherent live recalculation, compare paper/forms/cost trade-offs, select a plan, inspect its layout and export it. The new UI must use one versioned application state and a clean rendering layer rather than rearranging the legacy DOM. Complex mixed-format and multi-product layouts remain a separate bounded solver programme after the clean uniform workflow is usable.
