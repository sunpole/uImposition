# uImposition — полная UI/UX-перестройка рабочего приложения

Статус: **обязательный блокирующий этап перед дальнейшим расширением UI M7.6**.

Связанная задача: [Issue #58](https://github.com/sunpole/uImposition/issues/58).

## 1. Решение владельца

Текущий интерфейс нельзя считать законченным рабочим программным продуктом.

Проблема не сводится к размеру шрифтов или отступов. Текущая страница объединяет в один длинный поток:

- маркетинговый hero;
- настройки листа и изделия;
- геометрию;
- вместимость;
- ввод заказов;
- пары страниц;
- прайс;
- редактор целей;
- каталог вариантов;
- выбранный план;
- схемы;
- отчёт;
- PDF;
- milestone/status/roadmap для разработчика.

Пользователь не видит ясного рабочего окна, текущего этапа и главного действия. Поэтому дальнейшее добавление таблиц, solver-функций и карточек поверх существующей структуры запрещено до создания нового application shell.

## 2. Главная продуктовая цель

Оператор должен пройти полный рабочий путь без чтения документации и без поиска нужного блока по длинной странице:

```text
создать расчёт
→ ввести параметры заказа
→ исправить ошибки
→ рассчитать варианты
→ сравнить решения
→ выбрать план
→ проверить схемы и отчёт
→ скачать PDF
```

В любой момент должны быть понятны:

1. где пользователь находится;
2. что уже заполнено;
3. что требуется исправить;
4. какое действие является следующим;
5. какой вариант рекомендован;
6. какой вариант выбран оператором;
7. где открыть схемы, отчёт и экспорт.

## 3. Что удаляется из основного рабочего потока

Следующие элементы не должны занимать рабочие экраны оператора:

- большой маркетинговый hero;
- подписи этапов разработки `M2`, `M7.2`, `M7.5`;
- milestone panel;
- roadmap panel;
- тексты о будущих алгоритмах рядом с основными результатами;
- постоянные подробные формулы;
- доказательные developer-status блоки;
- дублирующие карточки одной и той же метрики;
- полные таблицы и схемы, раскрытые без запроса пользователя.

Эти сведения переносятся в:

- `О программе`;
- `Технические ограничения`;
- `Диагностика`;
- репозиторий и документацию.

## 4. Целевая информационная архитектура

### 4.1 Верхняя панель приложения

Постоянная компактная строка:

- логотип `uImposition`;
- имя или статус текущего проекта;
- индикатор сохранения в будущем;
- язык RU/EN;
- меню `⋯`;
- mobile menu при необходимости.

Здесь не должно быть рекламного заголовка.

### 4.2 Основная навигация

Пять рабочих разделов:

1. **Заказ**
2. **Проверка**
3. **Варианты**
4. **Выбранный план**
5. **Экспорт**

Дополнительные настройки открываются отдельно:

- цели оптимизации;
- профили машины;
- технические ограничения;
- диагностика;
- информация о версии.

### 4.3 Состояния разделов

Каждый раздел имеет статус:

- `не начат`;
- `требует внимания`;
- `готов`;
- `активен`;
- `недоступен до предыдущего шага`.

Навигация не должна скрывать ошибки и не должна притворяться завершённой, если данные неполны.

## 5. Desktop application shell

Целевой рабочий каркас:

```text
┌──────────────────────────────────────────────────────────────┐
│ uImposition · Проект без названия                 RU   ⋯     │
├──────────────┬───────────────────────────────┬───────────────┤
│ Навигация    │ Основное рабочее окно         │ Сводка        │
│              │                               │               │
│ 1 Заказ      │ Заголовок раздела             │ Готовность    │
│ 2 Проверка   │ Поля / таблица / варианты     │ Ошибки        │
│ 3 Варианты   │                               │ Выбор         │
│ 4 План       │                               │ Стоимость     │
│ 5 Экспорт    │                               │               │
│              │                               │               │
│ Настройки    │                               │               │
├──────────────┴───────────────────────────────┴───────────────┤
│ Краткий статус                         Основное действие     │
└──────────────────────────────────────────────────────────────┘
```

### Desktop-принципы

- левая навигация: 180–220 px;
- центральная рабочая область получает основное пространство;
- правая сводка: 240–300 px, может сворачиваться;
- primary action находится в предсказуемом месте;
- длинные таблицы используют доступную ширину, а не карточки по всей странице;
- подробности выбранной строки открываются в inspector или отдельном разделе;
- пользователь не прокручивает десятки независимых панелей.

## 6. Mobile application shell

На телефоне не переносится desktop-сетка целиком. Используется отдельный рабочий сценарий.

```text
┌──────────────────────────┐
│ uImposition       RU  ⋯  │
├──────────────────────────┤
│ 1 Заказ  2 Проверка ...  │
├──────────────────────────┤
│ Заголовок текущего шага  │
│                          │
│ Основной контент         │
│                          │
├──────────────────────────┤
│ Статус      Продолжить   │
└──────────────────────────┘
```

### Mobile-принципы

- один главный раздел на экране;
- sticky bottom action;
- шаги переключаются верхней полосой или компактным tab bar;
- никакого blur;
- никаких огромных hero и development-панелей;
- вспомогательные поля раскрываются по запросу;
- метрики показываются строками или компактной сеткой;
- варианты отображаются как компактные comparison rows;
- выбор плана открывает отдельный экран;
- схемы и отчёт используют вкладки;
- экспорт имеет отдельные ясные кнопки;
- критические действия имеют touch target не меньше 40–44 px;
- размер текста не уменьшается до нечитаемого ради плотности.

## 7. Раздел «Заказ»

### 7.1 Структура

Ввод делится на понятные группы:

1. Печатный лист
2. Изделие
3. Файлы и тиражи
4. Цветность
5. Прайс

### 7.2 Взаимодействие

- основные значения видны сразу;
- редкие настройки находятся в `Дополнительно`;
- пресеты и ручной ввод не конкурируют визуально;
- ошибки отображаются рядом с полем;
- сверху или сбоку показывается краткая готовность;
- основная кнопка называется **`Рассчитать варианты`**;
- автоматический промежуточный расчёт допускается, но не должен заменять понятное основное действие;
- после изменения данных результат получает статус `Требуется пересчёт`.

### 7.3 Строки заказа

Текущий textarea допускается временно, но должен выглядеть как импорт/быстрый ввод, а не как единственный конечный интерфейс.

Целевой вид:

- таблица строк;
- добавить;
- редактировать;
- дублировать;
- удалить;
- массовая вставка;
- ошибка одной строки не уничтожает остальные;
- сводка количества файлов, пар и тиражей находится рядом, а не отдельной большой панелью.

## 8. Раздел «Проверка»

Отвечает на вопрос: **можно ли запускать поиск вариантов?**

Показывает только значимые результаты:

- фактический лист;
- печатная область;
- занимаемый формат изделия;
- доступные сетки 0°/90°;
- количество позиций;
- количество файлов и печатных пар;
- ошибки и предупреждения;
- статус прайса;
- границу текущего solver scope.

Подробные формулы и точные пары страниц скрыты в раскрывающихся блоках.

Основное действие:

- `Рассчитать варианты`;
- недоступно только при реальном блокере;
- рядом объясняется причина недоступности.

## 9. Раздел «Варианты»

Это главный рабочий результат M7.6.

### 9.1 Основной вид

- одна строка на план;
- полный lossless-каталог по умолчанию;
- фиксированный набор главных колонок;
- остальные колонки настраиваются;
- сортировка по заголовку;
- фильтры в компактной toolbar;
- режим `Только различия`;
- recommendation и selection имеют разные визуальные признаки;
- выбор строки не является автоматическим подтверждением;
- отдельная кнопка `Выбрать план` или понятное действие строки.

### 9.2 Базовые колонки

По умолчанию:

- план;
- листы;
- формы;
- пластины;
- прогоны;
- перетираж;
- стоимость;
- статус;
- действие.

Расширенные:

- вес бумаги;
- component costs;
- unit cost;
- grid/rotation;
- family;
- proof status;
- split orders;
- imposition count;
- exact deltas.

### 9.3 Mobile view

На телефоне таблица превращается не в огромные карточки, а в компактные comparison rows:

```text
План A                         Рекомендован
20 листов · 4 формы · 20 пластин
240,05 BYN · +1 лист / −15 пластин
[Подробнее]                     [Выбрать]
```

По умолчанию видны только показатели, отличающие варианты.

## 10. Раздел «Выбранный план»

Отвечает на вопрос: **что именно будет производиться?**

### Структура

- название и статус выбранного плана;
- отличие от recommendation;
- ключевые метрики;
- предупреждения;
- вкладки:
  - `Сводка`;
  - `Схемы`;
  - `Отчёт`;
  - `Файлы и пары`;
- кнопка `Изменить выбор`;
- переход к экспорту.

Схемы не должны сразу растягивать страницу. Они открываются в отдельной вкладке/галерее.

## 11. Раздел «Экспорт»

Отдельный финальный экран:

- PDF схем;
- PDF производственного отчёта;
- будущий JSON проекта;
- имя файлов;
- количество страниц;
- статус генерации;
- ошибки;
- техническая граница экспорта.

Кнопки должны иметь ясные подписи и состояние загрузки.

## 12. Визуальная система

### 12.1 Иерархия

Использовать ограниченный набор уровней:

- app title;
- screen title;
- section title;
- field label;
- helper text;
- metric value;
- status text.

Нельзя использовать большие заголовки как основной способ разделения десятков блоков.

### 12.2 Surface roles

Визуально различать:

- app chrome;
- input surface;
- result surface;
- selected surface;
- warning/error surface;
- disabled surface;
- technical details surface.

### 12.3 Buttons

- **Primary:** продолжить, рассчитать, выбрать, скачать главный результат;
- **Secondary:** открыть подробности, изменить, повторить;
- **Quiet:** отменить, закрыть, свернуть;
- **Destructive:** удалить, очистить;
- icon-only кнопки только с понятной иконкой и accessible label.

Обычный текст, badge и кнопка не должны выглядеть одинаково.

### 12.4 Color and contrast

- спокойная нейтральная основа;
- один основной accent;
- отдельные semantic colors для success/warning/error;
- recommendation и selection не кодируются только цветом;
- disabled не должен выглядеть как обычный элемент;
- фокус всегда видим.

## 13. Состояния приложения

Для каждого раздела проверить:

- первый запуск;
- пустой заказ;
- частично заполненный заказ;
- ошибка поля;
- ошибка строки заказа;
- прайс отсутствует;
- расчёт готов;
- поиск выполняется в будущем;
- варианты найдены;
- вариантов нет;
- catalog truncated в будущем;
- выбран план;
- данные изменены после выбора;
- PDF создаётся;
- PDF готов;
- PDF failed.

## 14. Accessibility contract

Обязательно:

- логический tab order;
- один видимый `h1` на экран;
- реальные `label`;
- `fieldset/legend` для связанных групп;
- `aria-current` для навигации;
- `aria-live` для статуса расчёта и экспорта;
- ошибки связаны с полями через `aria-describedby`;
- controls работают с клавиатуры;
- drag-and-drop имеет кнопочную альтернативу;
- touch targets достаточного размера;
- контраст проверяется инструментально;
- zoom 200% не ломает основной сценарий;
- prefers-reduced-motion учитывается при анимации.

## 15. Архитектурная стратегия миграции

Полная UI/UX-перестройка не должна переписывать проверенную производственную математику.

Сохраняются:

- geometry models;
- orders parser;
- production plans;
- lossless catalog;
- ranking/objectives;
- runtime selection;
- production report;
- scheme renderer;
- PDF pipeline;
- existing calculation unit tests.

Меняются слоями:

```text
existing pure models
→ existing runtimes
→ new app state coordinator
→ new screen renderers
→ new app shell
```

### Запрещено

- переносить формулы в UI;
- дублировать production state в нескольких DOM-модулях;
- сохранять скрытую старую страницу как второй независимый интерфейс;
- менять solver одновременно с app-shell PR;
- смешивать полный redesign и release packaging в одном PR.

## 17. Acceptance criteria

Редизайн считается успешным только если:

1. на desktop пользователь сразу видит приложение, а не landing page;
2. на mobile первый экран показывает название, шаг и понятное действие;
3. ввод заказа находится в одном логическом разделе;
4. разработческие milestone/roadmap блоки отсутствуют в основном потоке;
5. пользователь понимает, почему расчёт недоступен;
6. варианты сравниваются в одном месте;
7. recommendation и selection различимы;
8. выбранный план открывается отдельным разделом;
9. экспорт находится в предсказуемом месте;
10. основной сценарий не требует прокрутки через все функции приложения;
11. desktop 1440/1024 и mobile 390/355/320 проверены Chromium-сценариями;
12. существующие unit и PDF regression остаются зелёными;
13. реальные screenshots визуально проверены владельцем или зафиксированы для его проверки;
14. интерфейс можно объяснить фразой: `введите заказ → рассчитайте → сравните → выберите → экспортируйте`.

## 18. Текущий приоритет

До завершения UX-1 и UX-2:

- не добавлять новые крупные панели;
- не продолжать карточечный M7.6 renderer;
- не расширять solver ради UI;
- не выпускать интерфейс как production-ready;
- использовать Issue #58 как главный UX blocker.
